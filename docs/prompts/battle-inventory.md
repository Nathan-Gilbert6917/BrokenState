# Battle map and inventory: session prompts

Seven sessions build one feature set on the tactical battle map and in the inventory: **vaulting half cover**, **windows that open, lock or break and new door types**, **loose rounds carried on people when teams are set up and goods change hands**, **moving kit between pockets, pack and rig in a fight for an action**, **reloading from pockets and rigs (the pack alone costs both actions)**, **handing items to the survivor next to you**, **makeshift lock picks** and **turning the survivor's figure by hand in the inventory**.

This file was written on 2026-10-17 from the owner's checklist (kept verbatim under "The requests") and a code survey of the same day. Where the request leaves a gap the "Reading" lines are the lead's call; a session that finds a reading impossible in the code stops and reports it in its Handoff instead of improvising. The sessions are run as agents by a coordinator who merges each one into `claude/battle-inventory` and then into `dev`.

## How to use this file

1. The file is committed on `claude/battle-inventory`. Each session runs in its own worktree branched from that branch (the coordinator merges its branch back).
2. A session reads **only this file, the Shared brief and its own section**, then the code it names.
3. Order: **Wave 1: A, C, F, G (parallel). Wave 2: B (after A) and D (after C), parallel. Wave 3: E (after C and D).**
4. Each session ends by appending a short **Handoff** note (real module and function names, anything that deviated, tests run) under its own section in this file, committed with its code.

Line numbers come from the 2026-10-17 survey and are approximate. Search by name.

# Session A: Vault over half cover

**Launch line:** `Read docs/prompts/battle-inventory.md. Do Session A only (Vault over half cover). Follow the Shared brief exactly.`

**Depends on:** nothing.

**Reading of the request:** a survivor (and a human enemy, for parity) can cross a half-cover cell that is `walk:false, cover:1` by vaulting it: the move path may pass over the cell but not end on it, the vault costs extra movement, and the move is tiring, so what is left of the unit's movement after the vault is less than a plain walk would leave. The dead do not vault (the climber keeps its own `climbOver`). Full cover is never vaulted. Windows are vaulted by Session B's rules, so for this session leave `window` and `smashed` out of the vaultable set (B adds them).

**Deliverables**
1. `combat.js`: a `VAULT` constant `{ COST: 2, OVER: true, NOISE: 1 }` or similar next to `MOVE`; a `vaultable(b, c)` predicate (half cover, `walk:false`, not a window, not `tall`, not a car with a unit on it, not a trap) and `canVault(u)` (player survivors and human enemies; not the dead; not with the **In arms** slot full, following the existing hands-full rules; not while prone/down if such a state exists). In `reachable`/`pathTo`: such a cell is passable for a vaulter at step cost `1 + VAULT.COST` (diagonal 1.5 + cost), **may not be the end cell** of a move, and keeps the no-corner-cutting rule. After `moveAlong` crosses a vaulted cell, the unit's movement for the rest of the turn is reduced: the simplest faithful rule is that a vault spends the action's remaining movement beyond the landing cell (land and stop) **or** charges `VAULT.COST` tiles of `mob`; pick one, name it in the Handoff, and make the reach bands show it.
2. Noise: a vault makes `stepNoise`-scale noise plus `VAULT.NOISE` (`b.noise`), not an `alertNear`. Sneaking units may still vault at the sneak mobility.
